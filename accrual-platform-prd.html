1. 项目概述

1.1 背景

现有计提平台存在计算逻辑与配置维护耦合、数据粒度粗、无法按业务线灵活配置公式等问题。本次新建独立计提平台，将数据处理与计提计算解耦，由数据组负责原始数据输出，平台组负责合同匹配、汇率转换、预估计算、手动调整、同步财务。

新平台核心改进点：

  • 支持5种计提类型（收入/成本/返点/返货/赔付）的统一管理
  • 支持4条业务线（miads含offline/miads不含offline/程序化/云端预装）的灵活选择与组合
  • 引入计提人（Accrual Person）维度，按人员隔离计提范围
  • 全流程可追溯：从选择条件到数据拉取、计算、调整、推送，每步均有记录

1.2 核心设计原则

原则说明
数据与计算分离数据组只负责原始数据输出，不参与计提计算逻辑
公式可配置每个业务线可独立配置预估计算公式，无需改代码
人工可干预预估结果支持手动调整，调整后可一键推送财务
合同信息复用CRM合同ID/账户/币种等信息从CRM读取，不重复维护
按计提人隔离启动计提时仅拉取该计提人负责的合同，避免跨人员干扰
全流程可追溯每一步操作（选择、匹配、计算、调整、推送）均记录日志，支持审计

2. 计提类型与业务线

新平台支持 5 种计提类型和 4 条业务线。不同组合决定了数据拉取方式、计算公式和推送财务的数据结构。

2.1 计提类型定义

计提类型 英文名 说明 数据来源 计算方法
收入计提 Revenue Accrual 按合同约定的分成比例，预估当月应确认的广告收入 Data Team base data (revenue field) Est Revenue = Revenue x (1 - Rebate Ratio) x Exchange Rate
成本计提 Cost Accrual 按消耗数据预估当月应确认的广告成本 Data Team base data (dsp_fee field) Est Cost = Spend x Cost Ratio x Exchange Rate
返点计提 Rebate Accrual 按合同约定的返点比例，预估当月应返还的返点金额 Data Team base data (rebate_ratio field) Est Rebate = Revenue x Rebate Ratio x Exchange Rate
返货计提 Return Accrual 预估当月因退货/退款产生的应冲减金额 Data Team return data Est Return = Return Amount x Exchange Rate
赔付计提 Claim Accrual 预估当月因广告赔付/争议产生的应确认金额 Data Team claim data Est Claim = Claim Amount x Exchange Rate

2.2 业务线定义

业务线 英文名 说明 包含数据范围 典型合同特征
miads（含offline） MIAds with Offline 小米广告平台全部广告形式，包含线上和线下（offline）广告位 线上消耗 + 线下消耗（offline DSP fee） 合同包含 offline ad slot 配置
miads（不含offline） MIAds Online Only 小米广告平台仅线上广告位，排除线下数据 仅线上消耗 纯线上广告合同
程序化 Programmatic 程序化广告投放，通过 RTB/ADX 等方式自动竞价 程序化广告消耗数据 RTB/ADX 类合同
云端预装 Cloud Preinstall 云端预装应用的分发数据，按预装量计提 预装激活数据 预装分发类合同

2.4 选择对下游的影响

数据拉取影响

维度影响说明

推送财务字段不同计提类型推送的财务字段结构不同（收入/成本/返点各有独立字段）

P2: Contract Match & Data Pull P0

1. 页面概述

系统自动执行合同匹配和数据拉取。用户在此页面查看匹配进度、匹配结果统计、未匹配合同列表，并可手动触发重新匹配。

2. 合同过滤逻辑

Filter Chain

步骤过滤条件数据来源
1按 Accrual Person 过滤合同CRM 合同表 WHERE accrual_person = selected_person
2按 Business Line 过滤合同CRM 合同表 WHERE business_line IN selected_lines
3按 Date Range 过滤合同有效期CRM 合同表 WHERE contract_start_date <= month AND contract_end_date >= month
4按 Contract ID 精确匹配（可选）CRM 合同表 WHERE contract_id = input_id
5按 DSP Level 过滤（可选）CRM 合同表 WHERE dsp_level1/level2 = selected

3. 数据拉取逻辑

Data Pull per Contract

维度说明
数据粒度按 Contract x Account x Media x Country x Day 拉取 base data
过滤条件business_line IN selected_lines AND date BETWEEN month_start AND month_end
关联方式通过 account_id 关联 CRM 合同表，一个 account_id 对应一个 contract_id
数据量控制单次拉取限制 10,000 行，超出时分页加载

Pushed Month已推送财务的月份，所有记录 status = "Locked"，Adjust 按钮置灰
Partially Pushed若部分合同已推送，已推送的记录锁定，未推送的仍可调整
Re-adjust After Push不允许。需先撤回推送（运维操作），再重新调整推送
P6: Push to Finance P0

1. 页面概述

用户确认预估结果后，一键推送到财务系统。推送前执行预校验，推送后锁定对应月份。

2. 推送前校验（Pre-push Validation）

校验项校验内容失败处理
Contract Matched所有选中合同均已匹配列出未匹配合同，阻止推送
Exchange Rate Configured所有涉及币种的汇率已配置列出缺失汇率的币种，阻止推送
Estimate Amount > 0预估金额不为零或负数（负数需额外确认）提示 "Zero or negative amount detected"
Month Not Locked目标月份未被锁定提示 "Month {YYYY-MM} is already locked"
Adjust Reason Complete所有有调整的记录均已填写原因列出缺失原因的记录

3. 推送 API 调用

Finance API Request

FieldTypeDescription
contract_idStringCRM 合同编号
accrual_monthString计提月份 YYYY-MM
accrual_typeEnumRevenue / Cost / Rebate / Return / Claim
est_amount_usdDecimal预估金额（USD），含调整后金额
original_currencyString原始币种
original_amountDecimal原始币种金额
exchange_rateDecimal使用的汇率
push_userString推送人用户名
push_timeTimestamp推送时间

4. 成功/失败处理

结果处理方式
Push Success记录 status = "Pushed"，该月份标记为 "Locked"，不可再调整
Push Failed记录 status = "Push Failed"，保留调整数据，支持重试
Partial Success部分合同推送成功，部分失败。成功的锁定，失败的可重试

5. 月份锁定规则

场景锁定行为
All Contracts Pushed该月份整体标记为 "Locked"，所有该月份的记录不可调整
Partial Push已推送的合同锁定，未推送的合同仍可调整和推送
Lock Release仅通过运维接口可释放锁定（需审批）

6. 边界处理

场景处理方式
Finance API Timeout记录状态为 "Timeout"，5 分钟后自动重试一次
Duplicate Push同一 contract_id + month + type 不可重复推送，提示 "Already pushed"
Concurrent Push使用乐观锁，推送时检查记录版本号，版本不一致则提示 "Data modified, please refresh"
